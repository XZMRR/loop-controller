## 摘要

本报告围绕两个核心问题展开前期调研：

1. 企业内控部门在人类组织中如何运作；
2. 当前 Agent 产品、架构与安全框架的发展现状。

调研发现，企业内控的核心在于 **"制度设计 + 分层防控 + 监督闭环"**，而非简单的事后审计；当前 Agent 安全方案虽然能力丰富，但普遍存在 **"重检测、轻设计，重审批、轻制度"** 的倾向。基于上述洞察，本项目提出 **Loop Controller** 的初步定位：

> **一个开源的、面向企业内控的 Agent 运行框架，通过"制度基础设施"让 Agent 在默认情况下做对，只在真正需要判断的边界处请求人类介入。**

本报告包含调研结论、项目定位、已确定事项及待确认的重点问题，供领导审阅与决策。

***

## 一、调研背景与目标

### 1.1 背景

随着大语言模型能力增强，AI Agent 正从"回答问题"走向"自主行动"。Agent 可以读取文件、调用 API、执行代码、发送消息，甚至与其他 Agent 协作。这种自主性带来了新的治理难题：

- 谁能证明这个 Agent 是谁、能做什么？
- 它的决策过程是否可追溯、可审计？
- 当它执行高风险动作时，如何确保可控？
- 当它出错时，如何快速止损并改进？

传统网络安全手段（沙箱、白名单、逐个确认）虽然有效，但容易陷入形式化：用户频繁点击"确认"却不理解含义，最终只实现了"出事能找到责任人"，并未降低风险发生概率。

### 1.2 调研目标

1. 理解企业内控部门的运作逻辑与核心方法；
2. 梳理当前主流 Agent 框架、协议与安全产品的能力边界；
3. 找到 Loop Controller 的差异化定位与可行切入点；
4. 为后续架构设计与 MVP 开发提供决策依据。

## 二、企业内控运作方式（简要结论）

企业内控不是"束缚业务"，而是通过控制风险来保障业务目标实现。其核心框架可概括为 **"三道防线 + COSO 五要素 + 信息化嵌入"**。

### 2.1 三道防线模型

| 防线    | 主体                | 核心职责             | 与 Agent 治理的映射                     |
| ----- | ----------------- | ---------------- | --------------------------------- |
| 第一道防线 | 业务部门 / 流程 Owner   | 在日常流程中识别、评估、控制风险 | Agent 的自我约束与工具选择限制                |
| 第二道防线 | 风控 / 合规 / 财务 / 法务 | 制定标准、嵌入控制、监督指导   | 框架级 Policy Engine、Guardrails、风险评估 |
| 第三道防线 | 内部审计 / 纪检监察       | 独立评价、缺陷整改、责任追究   | Audit Store、Trace、异常检测、人工审计       |

### 2.2 COSO 五要素

1. **控制环境**：诚信文化、治理架构、权责分配；
2. **风险评估**：识别、分析、响应影响目标实现的风险；
3. **控制活动**：审批、授权、核对、复核、职责分离；
4. **信息与沟通**：及时准确地收集、传递内控相关信息；
5. **监督**：持续监控、独立评估、缺陷整改。

### 2.3 关键启发

- 有效的内控依靠 **制度、环境和默认保护**，而不是每个动作都人工确认；
- 控制应 **前置发生**，而非仅事后审计；
- 每个员工都有清晰的 **岗位说明书和权限边界**；
- 行为必须 **可追溯、可审计**，但审计是为了改进制度。

## 三、Agent 产品与架构逻辑（简要结论）

### 3.1 Agent 的四大核心组件

| 组件           | 作用              |
| ------------ | --------------- |
| 规划（Planning） | 将复杂任务拆解为可执行子任务  |
| 记忆（Memory）   | 管理上下文与历史信息      |
| 工具（Tools）    | 连接外部系统与数据       |
| 执行（Action）   | 协调规划、记忆、工具的协同运作 |

### 3.2 主流框架

| 类型         | 代表                                   | 定位                |
| ---------- | ------------------------------------ | ----------------- |
| 生态型工具集     | LangChain / LangGraph                | 模块化、可组合、图状工作流     |
| 多 Agent 协作 | CrewAI / AutoGen / MetaGPT           | 基于角色/对话的团队协作      |
| 厂商原生       | OpenAI Agents SDK / Claude Agent SDK | 与自家模型深度集成，强调生产级能力 |

### 3.3 关键协议

- **MCP（Model Context Protocol）**：Agent 与外部工具/数据连接的"USB-C"标准；
- **A2A（Agent2Agent）**：Agent 之间横向协作的协议。

### 3.4 关键启发

- 生产级 Agent 的核心是 **Loop 控制**，包括终止条件、预算上限、 stagnation 检测、Checkpoint；
- 主流框架正在收敛到少量原语：Agent、Tool、Runner、Guardrail、Handoff；
- 现有框架主要解决"如何跑起来"，对"如何管得住"覆盖不足。

> 详细调研内容见附件二。

## 四、Agent 安全框架现状（简要结论）

### 4.1 分层防御已成共识

当前 Agent 安全方案普遍采用分层模型，核心能力包括：

| 层级        | 能力                       |
| --------- | ------------------------ |
| 身份与权限     | Agent ID、最小权限、短期凭证       |
| 沙箱与隔离     | 资源限制、网络白名单、容器化           |
| 运行时可观测性   | Trace、SIEM、异常检测          |
| 工具/插件供应链  | 签名验证、SBOM、SLSA           |
| RAG 与记忆安全 | 输入隔离、上下文清洗               |
| 红队测试      | 对抗提示、adversary emulation |
| 人机协同      | 风险自适应门控、可审计干预            |

### 4.2 OWASP Agentic Top 10（2026）

OWASP 发布的 Agentic 应用十大风险，是行业重要参考：

1. Agent Goal Hijack（目标劫持）
2. Tool Misuse and Exploitation（工具滥用）
3. Identity and Privilege Abuse（身份与权限滥用）
4. Agentic Supply Chain Vulnerabilities（供应链漏洞）
5. Unexpected Code Execution（非预期代码执行）
6. Memory and Context Poisoning（记忆与上下文污染）
7. Insecure Inter-Agent Communication（Agent 间通信不安全）
8. Cascading Agent Failures（级联失败）
9. Human-Agent Trust Exploitation（人类信任滥用）
10. Rogue Agents（失控 Agent）

### 4.3 典型攻击场景示例

以 **ASI01 Agent Goal Hijack** 为例，OWASP 给出了多个已发生或高度可信的攻击场景，说明传统"用户确认"模式已不足以保护 Agent：

| 案例                            | 攻击方式                                      | 核心危害                    |
| ----------------------------- | ----------------------------------------- | ----------------------- |
| **EchoLeak**                  | 攻击者通过邮件注入隐藏指令，Microsoft 365 Copilot 零点击执行 | 在用户无感知情况下外泄机密邮件、文件和聊天记录 |
| **Operator Prompt Injection** | 网页恶意内容被 Agent 在搜索/RAG 中处理                 | Agent 访问认证内页，泄露用户隐私数据   |
| **Goal-lock Drift**           | 恶意日历邀请周期性注入"quiet mode"指令                 | 在策略范围内逐步改变目标权重，引导低摩擦审批  |
| **Inception Attack**          | 恶意 Google Doc 注入指令                        | 外泄用户数据并诱导用户做出错误商业决策     |

这些案例说明：攻击者可以通过**间接提示注入、记忆污染、日程/文档等可信渠道**，在用户没有主动交互的情况下改变 Agent 行为。因此，仅靠"每次动作弹窗确认"无法解决根本问题，必须从 Runtime 层锁定目标、约束行为和审计漂移。

### 4.4 现有方案的不足

1. **重检测、轻设计**：强调运行中检测异常、事后追溯，未从架构上降低风险概率；
2. **重审批、轻制度**：依赖无差别的人工确认，用户疲惫、机制形式化；
3. **重单点、轻体系**：身份、沙箱、Guardrails、审计等能力分散，缺乏统一的制度表达层。

## 五、调研结论与项目定位

### 5.1 核心结论

1. 企业内控的本质是 **"通过制度设计降低风险"**，而不是"通过审批确认事后追责"；
2. Agent 安全领域已有丰富的单点能力（Guardrails、沙箱、可观测性），但缺乏 **统一的 Runtime 层治理框架**；
3. 现有方案容易陷入 **"审计损失"** 模式，未能真正解决 Agent 行为失控问题。

### 5.2 Loop Controller 的差异化定位

> **Loop Controller 不是另一个 Guardrails 产品或审批工具，而是 Agent 组织的"制度基础设施"。**

它借鉴企业内控思想，在 Agent Runtime 层提供：

- **Agent 身份与角色**：像"岗位说明书"一样定义每个 Agent 的能力边界；
- **Policy（制度）**：统一表达组织的权限规则、禁止行为、风险阈值；
- **风险评估与控制活动**：在任务执行前/中识别并控制风险；
- **可观测与审计**：完整记录执行链路，用于监督与制度改进；
- **人机协同**：只在真正需要判断的边界处请求人类介入。

### 5.3 与企业内控的映射

| 企业内控       | Loop Controller 中的实现                                |
| ---------- | --------------------------------------------------- |
| 第一道防线：业务自控 | Agent 自我约束、工具选择限制                                   |
| 第二道防线：框架风控 | Policy Engine、Guardrails、Risk Assessment、Checkpoint |
| 第三道防线：独立审计 | Audit Store、Trace、异常检测、人工审计接口                       |

## 六、已确定事项

| 事项      | 结论                                                                     |
| ------- | ---------------------------------------------------------------------- |
| 项目形态    | 先 SDK，后服务。第一版为 Python SDK，便于开源传播；SDK 预留 Governance Client 抽象，未来可对接远程服务 |
| 核心定位    | Agent 组织的"制度基础设施"                                                      |
| 设计哲学    | 制度优先于审批，预防优先于审计                                                        |
| 技术语言    | Python                                                                 |
| 与现有生态关系 | 原生 Runner + MCP 工具层，不包装其他框架，也不从零造工具生态                                  |
| 第一版场景   | "制度化的研究 Agent"：通过 Policy 定义 Agent 的读写权限、工具范围、风险规则；越权时自动拦截，必要时请求确认      |

## 七、待确认的大方向问题

以下问题直接影响后续架构设计与开发节奏，建议给予指导或确认。具体架构在architecture\overview\.md

### 问题 1：项目最终交付形态的期望

**说明**：Loop Controller 第一版将以 Python SDK 形式开源，但未来可以演进为独立服务（Governance Service），也可以始终作为可嵌入的库。不同的选择会影响架构设计和投入重点。请明确：公司希望先做一个**纯开源框架**，还是后续与公司**内部产品或平台集成**。

### 问题 2：项目周期与里程碑要求

**说明**：当前计划分为四个阶段：前期调研、架构设计、MVP 实现、开源准备。

### 问题 3：对"制度基础设施"这一差异化定位的认可度

**说明**：本项目最核心的差异化在于不做"审批工具"，而做"制度基础设施"。这意味着我们不会在每个动作上都弹窗确认，而是通过 Policy 定义 Agent 的默认行为边界。请确认这一方向是否符合预期。
