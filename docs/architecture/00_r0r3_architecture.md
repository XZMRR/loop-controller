# Loop Controller R0-R3 架构设计（v0.3）

> **文档定位**：在前期调研、测试和 2026-08-10 会议基础上，确定 Loop Controller 的核心架构分层。本版本把旧版"治理/编排/执行"三层模型更新为 **R0-R3 四层治理模型 + 基础设施层**，与 [`docs/research/内控最小岗位结构抽象_v0.1.md`](../research/内控最小岗位结构抽象_v0.1.md) 中的企业内控三道防线对应。
>
> **状态**：v0.3，已吸收 2026-08-10 会议关于 R2 策略引擎、R3 脱敏审计、Open-Core 边界的要求，待核心维护者评审后定稿。
> **最后更新**：2026-08-11

---

## 1. 设计原则

1. **制度优先于审批**：先定义 Agent 能做什么，让默认行为正确，只在边界处请求人类介入。
2. **Runtime 强制优先于模型自律**：Policy 由 Loop Controller 强制执行，不依赖 LLM 是否"听话"。
3. **R1/R2 实时执行不用大模型**：用确定性规则 + 专用小模型做判定和预检；R2 每次判定必须轻量、可解释、断网可用。
4. **R3 审计可用大模型，但异步**：R3 只采样审计，不阻塞主流程，不拥有任何指令下发权。
5. **人类只在 R0 和 R0-delegate 处做治理/审批决策**：制度由人类制定，例外由被授权的人类审批。
6. **默认拒绝与最小可用权限**：任何未明确允许的动作默认拒绝；CapabilityProfile 和 Earned Authority 都遵循最小可用原则。
7. **核心控制流程断网可用**：R1/R2 的实时判定、R3 的本地审计必须能在完全隔离/离线环境中运行。
8. **架构与沙箱解耦**：沙箱是可选的部署增强组件，不是 Loop Controller 的强制依赖。
9. **R1 不直接调用外部工具，R2 是工具调用的唯一授权出口**：R1 负责动作规划与申报，R2 作为 MCP Client Policy Gateway 校验并授权；任何对外部系统（MCP Server / API / 数据库等）的调用都必须由 R2 转发，R1 本身不持有可直接触发外部副作用的执行通道。

## 2. 商业模式：Open-Core 边界

Loop Controller 采用 **Open-Core** 模式，不是完全开源。

| 边界 | 开源部分 | 闭源部分 |
|------|----------|----------|
| **工程能力** | 沙箱接口、日志与审计、权限控制、R1/R2/R3 基础框架、Policy Compiler/Permission Interaction Analyzer/Earned Authority Manager 的运行时实现 | — |
| **意图控制接口** | — | 面向智能体备案/合规申报的意图控制接口服务（云端或私有化授权组件） |
| **数据壁垒** | 策略模板生成规则、风险案例上报协议、脱敏规范 | 官方策略库/风险案例库的内容资产 |

**说明**：

- **开源**：让社区和企业能够审计、嵌入、扩展通用工程层，建立信任和生态。
- **闭源**：意图控制接口作为核心能力保留，满足 Q4 智能体备案对"可控性"的合规要求，同时形成商业壁垒。
- **数据壁垒**：官方策略库/风险案例库通过"用户脱敏上报 + AI 推演生成"持续沉淀；用户自定义策略优先级高于官方策略。

## 3. 架构分层

```
┌─────────────────────────────────────────────────────────────────┐
│  R0 治理层（Governance Layer）                                    │
│  ┌─────────────────┐ ┌─────────────────────┐                     │
│  │ R0 Governance   │ │ R0-delegate         │                     │
│  │ 治理者           │ │ 被授权的审批代理人   │ 支持离线/异步审批   │
│  └─────────────────┘ └─────────────────────┘                     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  R1 执行层（Execution Layer）                                     │
│  ┌─────────────────┐ ┌─────────────────────┐                     │
│  │ R1 Agent        │ │ 轻量分类器           │                     │
│  │ 数字员工         │ │ 只输出风险信号       │                     │
│  └─────────────────┘ └─────────────────────┘                     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  R2 控制层（Control Layer / Policy Engine）                       │
│  ┌──────────────┐ ┌─────────────────────┐ ┌──────────────────┐  │
│  │ Policy       │ │ Permission          │ │ Earned Authority │  │
│  │ Compiler     │ │ Interaction       │ │ Manager          │  │
│  │ 规则编译器    │ │ Analyzer            │ │ 弹性自授权管理    │  │
│  └──────────────┘ └─────────────────────┘ └──────────────────┘  │
│  ┌─────────────────────────────────────────┐                     │
│  │ R2 Checkpoint                           │                     │
│  │ 统一策略执行点 + Encrypted Policy Store  │                     │
│  └─────────────────────────────────────────┘                     │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  R3 审计层（Audit Layer）                                         │
│  ┌──────────────┐ ┌─────────────────┐ ┌──────────────────────┐  │
│  │ Desensitizer │ │ Offline Audit   │ │ Budget Auditor       │  │
│  │ 脱敏/回填     │ │ 离线审计模式     │ │ Token + 财务双预算   │  │
│  └──────────────┘ └─────────────────┘ └──────────────────────┘  │
│  ┌─────────────────────────────────────────┐                       │
│  │ R3 Audit                                │                       │
│  │ 独立审计者 + 受控审计钩子                │                       │
│  └─────────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  基础设施层（Infrastructure Layer）                              │
│  Policy Store │ Audit Store │ Identity │ Tool Registry / MCP     │
│  （策略加密存储 │ 独立审计存储 │ 身份管理 │ 工具注册与 MCP 接入）   │
└─────────────────────────────────────────────────────────────────┘
```

**关于 Agent 交互与工具调用的分层说明**：

- **Agent 交互**（R1 主责）：Agent 与 User、其他 Agent、R0/R0-delegate、R2 之间的信息交换，包括任务接收、动作申报、审批请求、结果返回等。这些交互不产生直接的外部副作用。
- **工具调用**（R2 授权并转发）：任何对 Tool Registry / MCP Server / 外部 API / 数据库 / 文件系统的真实调用。R2 是唯一授权出口；R1 只申报，不直接执行。

## 4. 各层职责

### R0 治理层

| 角色 | 职责 | 人类/系统 | 关键规则 |
|------|------|----------|----------|
| **R0 Governance** | 定义风险偏好；批准 Policy 和审批权限分配；接收 R3 审计报告；决定是否整改 Policy | 人类 | 直接支付类动作必须路由到 R0，R2 不可直接放行 |
| **R0-delegate** | 实时接收 R2 转发的审批请求；批准/拒绝/修改请求；对高风险/不确定情况升级到 R0；支持离线/异步审批 | 被 R0 授权的人类 | 超出阈值自动向上路由审批 |

**会议细化要点**：

- 权限默认收缩至最小可用，并在 Policy 中强化"默认拒绝"表述。
- 直接支付场景（任何涉及真实资金/账户变动的动作）必须路由到 R0，R2 只能 `require_approval`，不能 `allow`。
- R0-delegate 可以是异步审批人，不要求 7×24 在线；离线审批的 pending 任务由 R1 挂起或降级执行。

### R1 执行层

| 角色 | 职责 | 人类/系统 |
|------|------|----------|
| **R1 Agent** | 接收任务并规划动作；依据 CapabilityProfile 自检；主动申报动作、参数、风险等级和理由；**不直接调用外部工具**；按 R2 / R0-delegate / R0 的决策执行经授权后的动作；返回结果 | 系统 |
| **轻量分类器** | R1 自检的辅助组件；用专用小模型做敏感信息预检、意图分类等；**只输出风险信号，不做最终强制** | 系统 |

**工具调用边界说明**：

- R1 与 User/其他 Agent/R0/R2/R3 之间的通信属于 **Agent 交互**，归 R1 主责。
- R1 对外部系统（Tool Registry / MCP Server / API / 数据库等）的任何调用请求都必须先封装为 **动作申报** 提交给 R2。
- R1 本身不直接持有外部工具的执行通道，避免 Agent 绕过策略执行危险动作。

**会议细化要点**：

- R1 基于能力手册（CapabilityProfile）做动作规划。
- 对低代码用户，CapabilityProfile/Policy 需要内置默认风险建议和模板，开箱即用。

### R2 控制层（策略引擎）

R2 不再只是简单的 allow/deny 判定，而是包含以下子系统的策略引擎。

| 角色/子系统 | 职责 | 人类/系统 |
|------------|------|----------|
| **R2 Checkpoint** | 接收 R1 申报并验证；返回 `allow / deny / modify / require_approval`；对 `allow` 的动作代理转发到 Tool Registry / MCP Server 执行；对需要审批的请求路由到 R0-delegate；记录所有判定日志 | 系统 |
| **Policy Compiler** | 将自然语言/声明式 Policy 编译为高效、可执行、可验证的规则表示（DSL/字节码/决策图）；支持版本控制与回滚 | 系统 |
| **Permission Interaction Analyzer** | 检测多个独立权限/工具组合后产生的新能力（A + B > C 的权限连锁反应），输出风险信号 | 系统 |
| **Earned Authority Manager** | 在 Agent 满足预设前提条件时动态提升其可用权限上限，但不得超过固定天花板（Fixed Ceiling） | 系统 |
| **Encrypted Policy Store integration** | 策略在持久化和传输时加密；R2 在受信执行环境中解密并执行，防止恶意 Agent 通过越狱探出完整控制逻辑 | 系统 |

**关键约束**：

- R2 判定必须轻量、确定性、断网可用，不依赖大模型。
- Policy 的编写/生成可以借助 AI，但实时判定必须使用编译后的可执行规则。
- 策略加密存储，运行时通过 HSM/TEE/密钥代理解密，防止 Agent 读取原始 Policy。

### R3 审计层

| 角色/子系统 | 职责 | 人类/系统 |
|------------|------|----------|
| **R3 Audit** | 异步、独立地收集 R1/R2/R0-delegate/R0 的过程日志；按风险偏置采样；评估控制有效性；生成审计报告并反馈给 R0；**只有建议权，无暂停/降级/修改配置等实操权限** | 系统（可用 LLM 辅助分析） |
| **Desensitizer** | 对日志中的敏感信息（PII、凭证、账户号等）进行掩码；在对外返回审计结果时按权限回填 | 系统 |
| **Offline Audit Mode** | 支持完全本地隔离部署，核心审计流程不依赖云端 | 系统 |
| **Budget Auditor** | 分别监控 Token 级运行预算和现实财务支付预算，超预算触发告警或熔断 | 系统 |
| **Audit Hook Controller** | 严格控制审计钩子数量与采样率，避免审计本身成为成本与性能瓶颈 | 系统 |

**关键约束**：

- R3 完全独立于 R1/R2，只读日志，**无指令下发权**。
- 敏感信息在日志中掩码，返回 R0 等授权方时回填。
- 审计钩子采用受控采样策略，高风险/首次异常/越权未遂优先采样。

### 基础设施层

| 组件 | 职责 |
|------|------|
| **Policy Store** | Policy、CapabilityProfile、Compiled Rule 的持久化；支持加密、版本、模板、用户自定义策略优先级 |
| **Audit Store** | 独立、不可篡改、可脱敏的审计日志存储 |
| **Identity** | Agent、用户、审批人的身份管理 |
| **Tool Registry / MCP** | 外部执行环境、工具注册表和 MCP 接入；Loop Controller 补充 MCP 缺失的工具级细粒度权限控制 |
| **Sandbox（可选）** | 可选的进程/容器级隔离执行环境；架构上与 R1/R2/R3 解耦，可按部署场景选择是否启用 |

## 5. 策略库与数据壁垒

策略库是 Loop Controller 的核心数据壁垒，参考杀毒软件的"主动防御 + 特征码库 + 应急响应"模式。

| 元素 | 说明 |
|------|------|
| **官方策略模板** | 内置默认风险规则模板，覆盖常见 Agent 场景（支付、数据访问、外部通信、权限提升等） |
| **用户自定义策略** | 用户自定义 Policy 优先级高于官方策略，满足企业内控个性化需求 |
| **脱敏上报** | 用户可选择将风险案例经脱敏后上报给官方，官方聚合后生成新的策略/案例 |
| **AI 推演生成** | AI 用于策略生成、案例推演和规则建议，**不用于实时判定** |
| **策略库更新机制** | 官方策略库周期性发布；用户自定义策略即时生效；更新支持版本回滚 |

## 6. 一次请求的典型流程

```
User → R1 Agent
        ↓
R1 Agent：轻量分类器预检 + CapabilityProfile 自检
        ↓
R1 Agent → R2 Checkpoint：申报动作 + 参数 + 风险等级 + 理由
        ↓
R2 Checkpoint：
   ├─ Encrypted Policy Store 解密并加载已编译规则
   ├─ Permission Interaction Analyzer 检查 A+B>C 组合风险
   ├─ Earned Authority Manager 计算当前动态权限上限
   └─ 验证 Policy
        ↓
   ├─ allow / modify → R2 Checkpoint 代理转发至 Tool Registry / MCP Server 执行，结果返回 R1 Agent
   ├─ deny → R1 Agent 返回拒绝原因
   └─ require_approval → R0-delegate 审批（支付类必须到 R0）
                           ↓
                高风险/不确定 → R0 Governance 升级
                           ↓
                R2 Checkpoint 按最终决策代理转发执行 / R1 Agent 返回拒绝原因
        ↓
R3 Audit：异步采集全流程日志（脱敏 → 掩码 → 风险偏置采样 → 审计报告）

**流程中的边界说明**：

- `R1 Agent → R2 Checkpoint` 的箭头是 **动作申报**，属于 Agent 交互。
- `R2 Checkpoint → Tool Registry / MCP Server` 的箭头是 **工具调用**，是真正产生外部副作用的动作。
- R1 与 User/其他 Agent/R0-delegate 之间的往返属于 Agent 交互，不经过工具调用通道。
```

## 7. 关键设计决策

| 决策 | 结论 | 原因 |
|------|------|------|
| R0-delegate 放在治理层 | R0-delegate 是被 R0 授权的人类，属于治理机制在运行时的延伸 | 与 R0 同为人类决策主体，区别于 R1/R2/R3 系统层 |
| R1/R2 实时执行不用大模型 | 用确定性规则 + 专用小模型 | 大模型判定不稳定（T1 测试已验证），不能作为企业级安全边界；R2 每次判定必须轻量 |
| R3 可用 LLM，但异步 | 异步采样审计，不阻塞主流程 | 审计允许更高延迟，可用 LLM 做异常分析；不影响执行效率 |
| 审批由 R2 触发 | R2 在验证 Policy 后判定是否需要人工审批 | 审批规则由 R0 制定，R2 执行，避免 R1 自己决定是否找审批人 |
| R1 主动申报 | R1 在自检后主动向 R2 提交动作和风险说明 | 体现第一道防线"自我控制"的内控思想 |
| Open-Core 边界 | 通用工程层开源，意图控制接口闭源 | 满足 Q4 智能体备案合规要求，同时建立开源生态 |
| 沙箱解耦 | 沙箱是可选组件，不强制 | 不同部署场景对隔离要求不同；核心控制流程不应依赖沙箱存在 |
| 策略加密 | Policy 在存储层加密，运行时受信解密 | 防止恶意 Agent 通过越狱探出完整控制逻辑 |
| 双类预算 | Token 预算与财务支付预算分开监控 | 两者性质不同，熔断/审批策略不同；支付类必须人类审批 |
| Agent 交互与工具调用分界 | R1 只做动作规划与申报；R2 是 MCP Client Policy Gateway，唯一对外工具调用的授权出口 | 防止 R1 绕过策略直接执行危险动作；工具调用是产生外部副作用的唯一边界，必须集中管控 |

## 8. 待确认问题

1. **Open-Core 边界细化**：意图控制接口具体形态是 R2 内的一个子模块，还是独立的云端/私有化服务？备案对接的 API 规范由谁提供？
2. **Policy Compiler 最终表达形式**：自然语言/声明式 Policy 最终编译为 DSL（如 Rego/Cedar）、字节码，还是生成 Python 代码？
3. **Earned Authority 机制**：是 Agent 完成特定任务后获得临时权限，还是基于实时风险评估动态提升权限上限？Fixed Ceiling 的默认值如何确定？
4. **权限连锁反应形式化**：Permission Interaction Analyzer 采用静态规则、图分析，还是基于能力集合的代数运算？需要多大程度上依赖理论形式化？
5. **用户上报数据流**：用户脱敏上报是异步上传到官方云端，还是可选本地沉淀？合规区域限制如何处理？
6. **MVP 范围**：是否仍然聚焦"制度化的研究 Agent"？会议提到优先 R1/R2/R3，R0-delegate 打桩，这一范围是否确认？

**已确认项**：

- R4 为误说法，架构保持 R0-R3 + 基础设施层。
- R3 发现严重违规时只能向 R0 提建议，**无实操权限（不能暂停/降级/修改配置）**。
- **MVP 决策记录（待核心维护者最终确认）**：
  1. **Open-Core 边界**：MVP 先用 **R2 内 hook（方案 A）** 打桩，接口设计成可切换为云端 SaaS（B）或私有化授权服务（C）。
  2. **Policy Compiler**：MVP 用 **Rego DSL（方案 A）** 起步，竞对调研中 OPA/Rego 是成熟路径；跑通后再评估是否自研字节码 VM（方案 B）。
  3. **Earned Authority**：MVP 先用 **任务完成后临时提升权限（方案 A）**，可解释性最强，便于向治理者/审计说明。
  4. **Permission Interaction Analyzer**：MVP 用 **静态规则表（方案 A）** 覆盖常见高危组合，同时预留图分析接口（方案 B）。
  5. **用户上报数据流**：MVP 用 **默认本地沉淀 + 可选匿名上报（方案 C）**，兼顾隐私合规与数据壁垒。
  6. **MVP 范围**：先选 **最小闭环 A**，优先跑通 R0-R3 核心循环；R0-delegate 打桩；若时间和人手允许再扩展。
