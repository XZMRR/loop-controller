## P0 — 必须修复

### P0-1：`wait_for_approval` / SSE / gRPC `_try_resume` 绕过 `ApprovalManager`，跨进程审批结果仍不可见

**问题描述**

`server.py` 与 `grpc_server.py` 的等待路径中，`_try_resume` 直接调用 `approval_store.get_request_by_id()` / `get_record()` 读取内存，没有走 `AsyncApprovalManager` 的封装方法，因此不会触发 `refresh()`。

后果：
- CLI 进程写入审批结果后；
- 运行中的 Runtime 进程内存里仍无该记录；
- `wait_for_approval` 长轮询、`SSE`、`gRPC wait` 会永远返回 `pending`，直到超时或 Runtime 重启。

规格 `v0.29.0_development.md §3.1.2` 原本以为这些路径会自然走 `controller.resume_after_approval` → `approval_manager.check()`，但实际未走此路径。

**涉及文件**

- `src/loop_controller/server.py` L491-L500
- `src/loop_controller/grpc_server.py` L504-L512

**修复要求**

1. 在 `server.py` `_try_resume` 中：
   - 将 `request = self._approval_store.get_request_by_id(decision_id)` 替换为 `request = self._controller._runtime.approval_manager.get_request_by_id(decision_id)`；
   - 将 `record = self._approval_store.get_record(decision_id)` 替换为 `record = self._controller._runtime.approval_manager.check(decision_id)`；
   - 若 `request` 为 `None`，返回 `None`；
   - 若 `record` 为 `deny`，按当前逻辑返回拒绝结果；
   - 若 `record` 为 `approve`，调用 `controller.resume_after_approval(request)`。

2. 在 `grpc_server.py` `_try_resume` 中做相同修改。

3. 确保 `AsyncApprovalManager` 已提供 `get_request_by_id(self, decision_id)` 方法，并在方法内先 `self.refresh()`。

**验收测试**

- 新增或扩展 `tests/test_server.py`：
  - `test_wait_for_approval_sees_cli_written_response`：直接以文件操作模拟 CLI 写入 `response` 行，不调用 Runtime 的 `record_response`，然后请求 `/v1/wait-for-approval`，断言返回 `approved` 而不是 `pending`。
- 新增或扩展 `tests/test_grpc_server.py`：
  - `test_grpc_wait_approval_sees_external_response`：同款 gRPC 断言。

## P1 — 强烈建议修复

### P1-1：`forward()` 对过期 reservation 未按规格处理，导致过期额度进程内永久滞留

**问题描述**

`get_pending_reservation` 现在对过期 reservation 返回 `None`（符合规格），但 `forward()` 随后进入"未预留"分支，直接调用 `reserve_for_execution` 创建**新的 reservation**。原过期 reservation 的额度仍然占用在 `_reserved` 计数中，进程内永不释放。

规格 `v0.29.0_development.md §3.2.2` 要求：
> `forward()` 查到的 reservation 若过期，按"未预留"处理——不 commit、不 refund，返回 `CheckpointError("reservation expired")` 并继续走正常 fail 路径（R1 修复后该路径会 `_refund_reservation` 兜底）。

**涉及文件**

- `src/loop_controller/checkpoint.py` L870-L876

**修复要求**

1. 在 `reserve_for_execution` 兜底之前，检测该 `call_id` 是否存在状态为 `pending` 或 `pending_approval` 但已过的 reservation：
   - 可新增内部辅助方法 `_get_expired_reservation_by_call_id(call_id)`；
   - 或让 `get_pending_reservation` 返回过期信息（但会改接口，不推荐）。
2. 若存在过期 reservation，抛 `CheckpointError("reservation expired")`。
3. `forward()` 的 `except CheckpointError`（L956-L959）会统一 `_refund_reservation(reservation)`，因此过期 reservation 会被 refund + 释放额度。

**验收测试**

- `tests/test_checkpoint.py` 新增 `test_forward_expired_reservation_refunded_and_raised`：
  - 构造一个 `pending` reservation 且 `expires_at` 已过期；
  - 调用 `forward()` 断言抛 `CheckpointError` 且消息包含 `reservation expired`；
  - 断言原 reservation 被 transition 为 `refunded`；
  - 断言预算 `_reserved` 计数恢复。

### P1-5：`_read_lines_from` 偏移计算在 Windows CRLF 下不精确

**问题描述**

`approval_store.py` L166 用 `len(line.encode("utf-8"))` 手工计算字节偏移。Windows 文本模式下写入的 `\n` 落盘为 `\r\n`，读时转回 `\n`，导致 `new_offset` 比真实偏移少 1 字节/行。当前靠 L169-L170 的 `if not text: continue` 兜底，但依赖未承诺的文本模式 `tell()` 语义。

**涉及文件**

- `src/loop_controller/infra/approval_store.py` L166

**修复要求**

1. 读完最后一个完整行后，直接使用 `fh.tell()` 作为 `new_offset`；
2. 移除对 `len(line.encode(...))` 的字节长度计算；
3. 保持 `refresh()` 调用后 `self._read_offset = new_offset` 不变。

**验收测试**

- `tests/test_approval_store.py` 新增 `test_refresh_offset_accurate_after_crlf`：
  - 在临时目录构造文件，手动写入 `\r\n` 行结束符；
  - 用 `JsonlApprovalStore` 写若干行后 refresh；
  - 再用另一个实例 append 新行，断言 refresh 能正确读取新增行。
