```text

  ↓

  ├─ 失败：写原 Audit → critical alert → degraded
  └─ 成功：写 Audit

```

## 3. 问题一：Audit 写入失败后未降级且可继续分叉

### 3.1 当前问题

当前 `_append_serialized()` 的顺序是：

```text
_prepare_event() 增加 Audit seq
  ↓
EvidenceChain.append() 成功并推进 Evidence 尾状态
  ↓
_write_audit_line()
  ↓
_write_checkpoint()
```

`_write_audit_line()` 没有异常处理。如果审计文件因磁盘满、权限变化、设备错误或路径异常而写入失败：

- SignedEvidence 已经落盘；
- EvidenceChain 的 seq/hash 已经推进；
- AuditStore 的 `_seq` 已经递增；
- Audit JSONL 没有对应记录；
- checkpoint 没有更新；
- `evidence_status` 没有立即变为 `degraded`；
- 异常向调用方传播，调用方可能误以为整个操作未执行；
- 后续 append 会继续使用已经推进的 seq，扩大 Audit/Evidence 分叉。

### 3.2 相关位置

- `src/loop_controller/infra/audit_store.py`：`_append_serialized()`；
- `src/loop_controller/infra/audit_store.py`：`_write_audit_line()`；
- `src/loop_controller/audit/evidence.py`：`EvidenceChain.append()`。

### 3.3 修复要求

必须单独处理“Audit 写入失败，但 Evidence 已经成功”的状态。

建议增加统一失败处理：

```python
def _handle_audit_write_failure(self, exc: Exception, event: AuditEvent) -> None:
    reason = f"audit write failed after evidence commit: {exc}"
    self._mark_evidence_degraded(reason)
    self._save_evidence_alert(
        rule_id="audit_write_failed_after_evidence_commit",
        title="审计写入失败，证据已提交",
        description=reason,
        event=event,
    )
```

要求：

1. 捕获 `_write_audit_line()` 异常；
2. 立即将 Evidence 状态标记为 `degraded`；
3. 写 critical alert；
4. 不删除已经写入的 Evidence；
5. Store 必须进入“不可继续安全追加”的状态，例如 `write_blocked=True`；
6. 在完成显式恢复或重建 Store 前，后续 append 必须 fail-closed，不能继续推进 seq；
7. health 接口立即返回 `evidence_status=degraded`；
8. 错误信息不得包含 Secret、token 或证书内容。

仅标记 degraded 但继续写入仍不够，因为 Audit 和 Evidence 已经发生单边提交，继续追加会扩大损坏范围。

### 3.4 恢复边界

v0.26.1 不需要实现自动跨文件事务回滚。允许采用以下简单语义：

```text
Audit 写失败
  ↓
Store 标记 degraded + write_blocked
  ↓
拒绝后续审计追加和需要审计的业务执行
  ↓
运维修复文件系统
  ↓
重启 Runtime 或显式执行一致性恢复
```

如果治理操作要求“审计失败不能继续执行”，则上层应得到明确的审计不可用错误，禁止继续触发新的工具副作用。

### 3.5 验收测试

- monkeypatch `_write_audit_line()` 抛出 `OSError`；
- Evidence 只增加一条，Audit 不增加；
- health 无需重启立即变为 degraded；
- critical alert 存在；
- 后续 append 被拒绝，不继续增加 Audit/Evidence seq；
- 修复文件系统并重建 Store 后，启动验证能明确报告单边记录；
- 调用方不会安全重试已经可能产生副作用的业务。

## 4. 问题二：明确 checkpoint 落后语义

### 4.1 当前问题

当前启动验证只拒绝：

```text
当前 Audit/Evidence seq < checkpoint seq
```

当文件尾部已经是 N，而 checkpoint 停留在 N-1 时：

- Audit 和 Evidence 彼此一致；
- 当前 seq 大于 checkpoint seq；
- checkpoint hash 检查被跳过；
- `verify_evidence_chain()` 会把运行期 degraded 重置为 healthy。

这可能来自合法的 checkpoint 原子替换失败，也可能来自旧 checkpoint 回放。纯本地 checkpoint 没有外部可信时间或单调计数器，无法抵抗攻击者同时回放完整旧快照。

### 4.2 本版本采用的明确语义

v0.26.1 采用以下恢复语义：

> **Audit 和 Evidence 两条完整链彼此一致且严格前进时，允许 checkpoint 落后，但必须验证旧 checkpoint 确实锚定当前链中的历史位置，然后重建最新 checkpoint。**

这样既避免把一次 checkpoint 写失败永久变成不可恢复状态，也避免完全忽略旧 checkpoint。

### 4.3 修复要求

当当前尾 seq 大于 checkpoint seq 时：

1. 读取 checkpoint 中的 `audit_seq` 和 `evidence_seq`；
2. 要求两者相等；
3. 在 Audit 链中定位该历史 seq，验证该位置的累积 Audit hash 等于 `checkpoint.audit_hash`；
4. 在 Evidence 链中定位该历史 seq，验证该记录的 `current_hash` 等于 `checkpoint.evidence_hash`；
5. 确认 checkpoint 之后的 Audit 和 Evidence 记录仍然一一对应并完整延伸到当前尾部；
6. 全部成立后，原子重建指向当前尾部的新 checkpoint；
7. 重建成功后才能恢复 healthy；
8. 任一检查失败则保持 degraded，不得自动覆盖 checkpoint。

以下情况必须失败：

- Audit seq 与 Evidence seq 不一致；
- checkpoint 只锚定其中一条链；
- checkpoint hash 不匹配历史位置；
- checkpoint seq 超过当前文件尾；
- checkpoint 后两条链事件不一致；
- checkpoint 签名无效。

### 4.4 已知限制

即使完成上述修复，以下攻击仍无法仅靠本地文件检测：

```text
攻击者同时回放：
- 历史 Audit 前缀；
- 对应历史 Evidence 前缀；
- 当时签名有效的历史 checkpoint。
```

三份本地状态完全自洽时，需要远程不可变锚点、可信单调计数器或 KMS/HSM 才能检测。该限制继续留到 v0.27+，不得宣传为本版本已解决。

### 4.5 验收测试

- checkpoint N-1、Audit/Evidence 为 N，旧 checkpoint 正确锚定历史位置：验证并重建到 N；
- checkpoint N-1 的历史 Audit hash 被篡改：验证失败；
- checkpoint N-1 的 Evidence hash 被篡改：验证失败；
- checkpoint seq 大于文件尾：验证失败；
- checkpoint 落后且 Audit/Evidence 后缀不一致：验证失败；
- 重建 checkpoint 失败：保持 degraded；
- 只有重建成功后状态恢复 healthy。

## 5. 问题三：`seal()` 缺少并发原子性

### 5.1 当前问题

`seal()` 当前在共享写锁之外读取：

```python
chain_hash = self._chain_hash
```

随后构造 seal 事件，最后才调用 `append(event)` 获取统一写锁。

可能发生：

```text
线程 A：seal() 读取 H1
线程 B：append() 写入普通事件，链尾变成 H2
线程 A：append(seal)，seal 的 prev_hash 为 H2
```

最终 seal 中：

```text
metadata.chain_hash = H1
seal.prev_hash = H2
```

`verify_chain()` 会判定 seal 无效，使合法并发直接破坏审计链。

当前 Runtime 没有自动调用 `seal()`，但它是公开 API，定时任务或运维线程并发调用时可触发。

### 5.2 修复要求

以下步骤必须位于同一个 `_sync_lock` 持有周期：

```text
获取锁
  ↓
读取当前 _chain_hash
  ↓
生成 seal_signature
  ↓
构造 AuditEvent
  ↓
分配 seq / prev_hash
  ↓
写 Evidence
  ↓
写 Audit
  ↓
写 checkpoint
  ↓
释放锁
```

不要在 `seal()` 外层获取当前普通 `threading.Lock` 后再调用 `_append_serialized()`，否则会因为锁不可重入而死锁。

建议提取锁内方法：

```python
def _append_locked(self, event: AuditEvent) -> None:
    """调用方已持有 _sync_lock。"""
    ...

def _append_serialized(self, event: AuditEvent) -> None:
    with self._sync_lock:
        self._append_locked(event)
```

然后：

```python
def seal(self, reason: str = "periodic_seal") -> AuditEvent:
    with self._sync_lock:
        chain_hash = self._chain_hash
        event = self._build_seal_event(chain_hash, reason)
        self._append_locked(event)
        return event
```

### 5.3 验收测试

- 多线程并发执行普通 append 和 seal；
- 重复执行至少 100 轮；
- 不发生死锁；
- 每条 seal 的 `metadata.chain_hash == prev_hash`；
- `seal_signature` 验证通过；
- 最终 `verify_chain()`、Evidence 验证和 checkpoint 验证全部通过。

## 6. 问题四：Harness API Key 仍未进入 Secret 吊销

### 6.1 当前问题

`HarnessExecutor.secret_refs_for()` 仍固定返回：

```python
return []
```

但 HTTP Harness Backend 会：

1. 从 `HTTPBackendConfig.api_key_env` 获取环境变量名称；
2. 从进程环境读取真实 API Key；
3. 使用 `x-harness-api-key` 请求头发送给 Harness。

该环境变量名称属于 Loop Controller 实际使用的可信 Secret 引用。当前统一吊销检查无法看到它。

触发路径：

```text
HTTP Harness 配置 api_key_env=HARNESS_API_KEY
  ↓
管理员吊销 secret HARNESS_API_KEY
  ↓
HarnessExecutor.secret_refs_for() 返回 []
  ↓
RevocationList 未命中
  ↓
请求仍携带已吊销 API Key 发往 Harness
```

### 6.2 修复要求

`HarnessExecutor` 必须保存原始后端配置：

```python
self._backend_configs = dict(backends)
```

根据工具绑定关系提取可信 Secret：

```python
def secret_refs_for(self, tool_name: str) -> list[str]:
    spec = self._tool_specs.get(tool_name)
    if spec is None:
        return []

    config = self._backend_configs.get(spec.harness)
    refs = set(spec.secret_refs)
    if isinstance(config, HTTPBackendConfig) and config.api_key_env:
        refs.add(config.api_key_env)
    return sorted(refs)
```

如 `HarnessToolSpec` 当前没有显式业务 Secret 字段，增加：

```python
secret_refs: list[str] = Field(default_factory=list)
```

要求：

- `api_key_env` 作为后端认证 Secret 引用；
- `HarnessToolSpec.secret_refs` 作为工具业务 Secret 引用；
- 普通环境变量不能自动全部视为 Secret；
- 只返回 Secret 引用名称，不返回真实值；
- 未注册工具时返回空列表或现有受控结果，不能让吊销预检查提前抛出未处理 `KeyError`；
- 多个工具绑定不同 Backend 时不能串用 Secret 引用。

### 6.3 验收测试

- HTTP Harness 配置 `api_key_env=HARNESS_API_KEY`；
- 调用参数不包含 `secret_ref`；
- 吊销 `HARNESS_API_KEY` 后，Harness HTTP Mock 调用次数为 0；
- 移除吊销后恢复执行；
- 两个工具绑定不同 Harness Backend，Secret 引用正确隔离；
- Subprocess Harness 没有 Secret 配置时返回空列表；
- 显式 `HarnessToolSpec.secret_refs` 与 Backend API Key 引用合并去重；
- 审计中只出现引用名称，不出现 API Key 值。

## 10. 保留的系统边界

本轮修复完成后仍不承诺：

- 多进程或多 worker 同时写同一 JSONL 文件安全；
- 攻击者同时回放历史 Audit、Evidence 和有效旧 checkpoint 时可被本地系统检测；
- 本地 checkpoint 等同于远程 WORM 或可信单调锚点；
- Agent 在不受控环境中无法绕过 Loop Controller；
- 本地 Secret 和 Ed25519 私钥达到 KMS/HSM 的保护等级。

这些能力继续留给 v0.27+。
